# Claude instructions for this repo

Read `README.md` before making non-trivial changes — it explains the architecture, naming vocabulary, and generated-data boundaries this project depends on. Read `STYLE.md` before writing or refactoring TypeScript — code-shape rules (classes over function modules, getters over returned state bags, dead-code deletion) distilled from the user's own refactors of AI-generated code. The short version:

- **`src/00_*`–`06_API/` are a generic Sheets+Apps-Script framework; `src/businessEndpoints.ts`/`src/businessEndpoints/` are the only place real-estate-specific logic belongs.** Dependencies only point downward by folder number — never import from a higher-numbered tier. `businessEndpoints.ts`/`businessEndpoints/` sit outside the numbering (like `utils/`) and may import from any tier. `businessEndpoints.ts` is the registry; `businessEndpoints/` holds one file per endpoint, and `businessEndpoints/BusinessOperators/` holds any classes they need.
- **`02_SpreadsheetRaw`'s classes are raw-index Sheets API access only** — whole rows/columns by GID + index, sheet properties, and `UniformRowRaw`. They never resolve a column by name or `columnId`; that's `03_SpreadsheetIndexed`/`04_SpreadsheetNamed`'s job. The tier's sheet chain is `SheetRawBase` → `SheetCommonRaw` (abstract; the members both sheet views use) → `SheetRaw`/`SheetMetaRaw`; the extra level is deliberate, because the row and column base classes hang off `SheetRawBase` and two of `SheetCommonRaw`'s members would be illegal overrides there — don't fold it back in. The folder also holds `SpreadsheetSchema.ts` (next bullet), which does resolve columns — it lives there because it must sit below both tiers that use it, and Raw classes are limited to `SpreadsheetSchema` by convention, not by the import graph. Generating/updating `01_generatedConfigs` is a separate `05_Operators` tier's job (`SheetConfigOperator`/`ColumnConfigOperator`/`ValueConfigOperator`, coordinated by `ConfigOrchestrator`) — config maintenance is neither Raw's nor Named's responsibility.
- **Three schema classes, one accessor.** `SpreadsheetSchema`/`SheetSchema`/`ColumnSchema` all live in `src/02_SpreadsheetRaw/SpreadsheetSchema.ts` — one module, because they form an import cycle that would crash at Apps Script runtime if split. Every class that has a schema exposes it as `schema`, narrowed to its level (spreadsheet, sheet/row, or column/cell); `baseSchema`/`ssSchema`/`columnSchema`/`sheetSchema` are gone. Build one via `SheetSchema.fromSheetName`/`.fromSheetGid` or `ColumnSchema.fromColumnName`/`.fromColumnId` — name-addressed gets full literal precision, GID-addressed gets the widened default. `SheetSchema` and `ColumnSchema` are siblings, not parent and child. See README's "The schema classes".
- **The column declares what `value` means; `valueNotEmpty` and `valueOrEmpty` are the marked forms.** On Named's cells, columns and rows, `value`/`valueArr` are blank-excluding-and-throwing on a column whose Column Config **Empty value allowed** box is unticked, and blank-tolerant on one where it is ticked (#13). `valueNotEmpty`/`valueArrNotEmpty` always exclude `""` and throw naming the blank cell, on every column; `valueOrEmpty`/`valueArrOrEmpty` always keep `""` for a caller that has decided what blank means, and `valueArrFilterEmpty` drops the blanks. **Indexed offers no unmarked word** — it resolves columns by generated id and cannot see a declaration, so it has `valueNotEmpty`/`valueArrNotEmpty` and the blank-tolerant pair only. Raw offers nothing shorter than `valueOrEmpty`/`valueArrOrEmpty`, and so does a uniform row at any tier. Reach for a marked name only where the call site's requirement genuinely differs from its column's. A column declared as Checkbox in Sheets is the one exception to the blank existing at all: its value name is `checkbox`, its value type is exactly `boolean`, and its blanks read as `false`, so a selector reads through the unmarked accessor whatever its box says. A column that merely holds `TRUE` without declaring the type stays `boolean` and keeps its blank. The trait shapes the accessor and never the column value type, and it is enforced at access, never at fetch. Writes never validate at all, so a blank is writable into any column whatever its box says. See README's "Naming vocabulary".
- **An in-app date is a `DateSerial` — a whole-day Sheets serial — not a JS `Date`.** A `date` column's `value` is a branded count of whole days from the Sheets epoch, so a currency `number` can't be passed where a date is wanted (#15). `Dat` is the calendar-day module and takes and returns serials only: build with `Dat.fromYmd`/`Dat.today`, move with `Dat.addDays`/`addMonths` rather than `+ 1`, and don't convert to `Date` at the read line. `Val.validate.date` delegates to `Dat`, `Tim` stays the datetime module and imports its timezone, epoch and day length from `Dat`, and `Dat` imports neither. Sheets still stores plain numbers and the operator's column type is still "date"; declared `TIME`/`DATE_TIME` columns map to `number`. See README's "Naming vocabulary".
- **Never run `clasp push`, `clasp run`, `clasp deploy`, `npm run build`, or `npm run gen:configs` without asking first.** They affect a live Apps Script deployment. `npm run gen:configs` doesn't just read — it writes to the live Sheet Config/Column Config sheets and to business sheets' header rows (missing column IDs), then atomically regenerates `sheetConfigs.ts`/`columnConfigs.ts`/`valueConfigs.ts` together, all three or none. Never run a partial/older regeneration path that updates a subset instead — see README.md's "Generated data" section for why. `npm run tsc` is always safe, as is `npx tsc --noEmit --extendedDiagnostics` for measuring type-check cost. When the sheet's shape is what's wrong, the fix is the sheet plus a regeneration, not a compensating workaround in code — propose it that way round. And a regeneration reflects the sheet at the moment it ran: edit the sheet afterwards and the configs are silently stale, since `npm run tsc` passes either way. After any sheet change, read the regenerated entry before building on it.
- **Commit to `master` by default; don't branch off it as a reflex.** This overrides the harness default of branching whenever the current branch is the default one. Branch only when the user asks for one, or when the repo shows work already in flight — uncommitted changes you didn't make, a branch ahead of `master`, a merge or rebase in progress, or a commit you didn't write appearing since the session began. In that second case, **ask which the user wants before writing** rather than deciding for yourself. Commit or push still only when asked.
- **Verify a type-level claim with an identity check, not an assignment** — an assignment passes against `any` and against `never`, so it proves nothing about a mapped or conditional type. Use `IsExactly`/`assertType` (or `assertNotType`, for "these two types differ") from `src/testSupport/typeAssertions.ts`, and treat any probe that needed an `any` to compile as having proved nothing. See STYLE.md's "Type modeling" and README's "Type-check cost."
- **The `gsheets` MCP's read tools (`list_spreadsheets`, `list_sheets`, `get_sheet_data`) are always fine.** Any write tool (`create_spreadsheet`, `create_sheet`, `update_cells`, `batch_update_cells`) needs a stated specific plan — exact sheet/range/values, or exact new sheet/spreadsheet — and explicit permission first, not a general go-ahead. `share_spreadsheet` needs its own separate confirmation of exactly who and at what permission level, since it grants access rather than just changing data.
- **Don't hand-edit the generated data** in `sheetConfigs`/`columnConfigs`/`valueConfigs` (`src/01_generatedConfigs/`) — regenerate from the spreadsheet instead, per README. Exception: `sheetConfigs`/`columnConfigs` entries for the config-describing sheets themselves (`sheetConfig`, `columnConfig`, `spreadsheetConfig`, `valueConfig`) form a guaranteed floor and are meant to stay fixed rather than be regenerated away (see README).
- **An endpoint is one entry keyed by the column whose action-row checkbox triggers it** — any column, no suffix requirement. The entry's value is an object: a required `action`, plus optional `timeLastRan` and `runStatus` column names, an optional `selector` object (a required checkbox-column `column`, plus `retainSelection` and `requireOneRow`), and `runOnUncheck`. **Every flag is a directive to the framework, never a description of the entry** — that one mood is why they read `retainSelection`/`requireOneRow`/`runOnUncheck` rather than `retainsSelection`/`runsOnUncheck` (#18). Each key carries its own sheet, so every column it names is constrained to that sheet and to the value type it needs; a cross-sheet or wrongly-typed column is a compile error, and both selector flags are unnameable on an endpoint with no selector. Without `runOnUncheck` the entry checkbox is a **run button** and clears itself on the run's setup flush; with it, the endpoint fires on tick *and* untick and the box is left alone. A declared `selector` prunes the sheet to the ticked rows, and `timeLastRan`/`runStatus` are stamped into those rows (or into every table data row when there's no selector). `requireOneRow` fails a run with more than one ticked row, as the first statement inside the run's `try`, so the refusal reads as an ordinary failed run and the selection survives it. **A successful run consumes its selection** — the ticks are cleared to an explicit `false` inside the run's `try`, so a failure discards the clearing along with the rest of the action's queued changes — unless the selector declares `retainSelection`. **An action returns a run report**: nothing, a string, or an object with an optional `runState`, an optional `message` and an optional `rows` map of per-row reports keyed by grid row index. The states are `running`, `success`, `warning` and `failure`, each paired with its colour in one object, and **both** feedback columns are painted in the state's colour. Warning and failure demand a message; an omitted state means success; the top-level state is only the default for rows the map doesn't name, and the framework derives nothing from the map. A per-row report is a per-cell write landing on top of the run-level fill in the same batch, and a key that isn't a data row of the sheet throws. A thrown failure still abandons the run and paints every row red; a *returned* failure means that row alone didn't go through while the rest of the run committed. `RowNamed.blankRequiredColumnNames` is how an endpoint asks which of a row's columns are blank and don't allow it. `EndpointRun` owns all of that; `Api` only decodes the event and dispatches. **One endpoint, one file**: `businessEndpoints.ts` is a registry of imported entries, and each entry's body lives in `businessEndpoints/<name>.ts` as a single exported `Endpoint<"thatSheet">` with module-private helpers, not a class (`buildLedger.ts` is the reference; update-terms is deliberately not migrated yet). Register endpoints with a plain `: Endpoints` annotation, never `makeStructuredConfig`, which silently accepts a key that isn't a real column. The three suffix strings in `spreadsheetConfig` are now **naming convention only** — nothing dispatches on them. See `CONTEXT.md` for what these words mean and README's "Endpoint dispatch" for how the dispatch is built.
- **A sheet never ends a run with zero data rows.** A delete that would take the count to zero clears that row in place instead, leaving one **blank row** whose formula cells are untouched — a Sheets table copies a new row's formulas, formats, validation and colours from the rows already there, so emptying a sheet destroys them permanently. Raw enforces it (`RowRaw.delete` throws), Indexed upholds it (`RowIndexed.delete` converts to `clearValues`), and `SheetIndexed.DELETE_ALL_DATA_ROWS()` is the only way to empty a sheet. Before adding a deletion path, read README's "A sheet never ends a run with zero data rows" — a new one that reaches zero is a bug, not a shortcut. The append path reuses the blank row, so don't "fix" a sheet by appending past it.
- **`Meta` is an axis on sheets and columns, not a fourth tier.** Every tier has both views: the **primary** one deals in contents and holds the unmarked name (`SheetRaw`, `ColumnNamed`, `RowIndexed`), the **Meta** one is the structure as its own shape (`SheetMetaRaw`, `ColumnMetaNamed`). `ss.sheet(name)` gives the primary sheet and `ss.sheetMeta(name)` the Meta one; within a view, plain nouns stay in that view, and crossing costs exactly one word — `meta` going one way, `primary` the other, with no cross-level shortcut. A new member belongs on the Meta class only if it *only* (1) acts on or reads from a uniform row, (2) samples the top data row for a column-wide fact, or (3) reads column-wide structure from the table's own column properties; otherwise it goes on the primary class, or on the tier's shared abstract sheet class if both views use it. See README's "Naming vocabulary" and "The sheet and column class chains".
- **A column is addressed either relatively (`<SN, CN>`) or absolutely (`ColumnFullName`), and there is deliberately no type-level bridge between them** — building one blows up the type-checker. Reach for the absolute family only when you need to name a *set* of columns cutting across sheets; everything sheet-scoped stays on `<SN, CN>`. See README's "Two ways to address a column".
- **Optimizing a trigger means removing a Sheets round trip — nothing else moves the number.** All API traffic funnels through `SpreadsheetRaw.fetchAllGathered`/`_sendUpdateRequests` (~250–450ms each); the framework's own CPU is ~20–60ms per run. `SpreadsheetApp` was measured as a cheaper alternative and is *slower*; don't re-propose it without new measurements. See README's "Round trips are the cost".
- **This code runs in Google Apps Script, not Node.** No Node/DOM APIs at runtime — only in build tooling.
- **Tests run on Vitest, safe to run freely.** `npm test` (or `npm run test:coverage`) never touches the live spreadsheet or Apps Script — everything it exercises runs against fakes. Co-locate a new test as `Foo.test.ts` next to `Foo.ts`; shared fakes for the ambient GAS globals (`Sheets`, `PropertiesService`, `ScriptApp`, `SpreadsheetApp`) live in `src/testSupport/`, outside the tier numbering like `utils/`. See README's "Testing" section for the mocking approach and what's covered so far. `npm run tsc` remains the whole *type*-verification story; run both before calling a change done.

Four prose files, four jobs. **README.md** is the map — what exists and where — and holds the **architecture** vocabulary (**Raw / Indexed / Named / Operator / Trait / Config / Schema**) under "Naming vocabulary". **CONTEXT.md** is the glossary of **domain** words (**endpoint / runner / two-way endpoint / selector / run status / run state**). **STYLE.md** is code shape. **DESIGN.md** is why the design is the way it is — read it before arguing that something looks missing or over-engineered; several of its principles exist specifically to stop a deliberate absence being helpfully filled in. Both vocabularies are used precisely; if you're placing or renaming a file and unsure which applies, ask rather than guess. **A plan or spec for non-trivial work includes its prose-file updates in its own scope** — README/STYLE/DESIGN/CLAUDE edits are part of the work, not a follow-up pass. A change that makes one of these four files wrong isn't finished until that file is right.

**During a design or grilling session, write nothing until the user invokes the skill that files it** — no code, no `CONTEXT.md` entry, no README edit. This overrides `/domain-modeling`'s instruction to capture a term the moment it settles: the GitHub issue is the system of record, and a term lands in the same pass as the spec that justifies it.

## Agent skills

### Issue tracker

Issues and specs live as GitHub issues in `ByronBroughten/Real-Estate-Manager---Apps-Script`, driven via the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

The five canonical triage roles, used verbatim as label strings. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: `CONTEXT.md` at the repo root, created lazily by `/domain-modeling`. **There is no `docs/adr/` tree, and none should be created** — DESIGN.md rules it out: specs are published as GitHub issues, and a second filing system would only drift from them. An architectural argument goes into DESIGN.md's principle list, cited by issue or commit. `/domain-modeling` will also tell you to record every resolved term in `CONTEXT.md` — that applies to **domain** words only, the operator-facing ones. Architecture vocabulary (tiers, class-shape axes like Meta/primary, member-placement rules) goes under README's "Naming vocabulary" instead; `CONTEXT.md` stays free of it. If the word would mean nothing to someone clicking a checkbox in the sheet, it isn't a `CONTEXT.md` term. See `docs/agents/domain.md`.

### Hidden skills

A skill marked `disable-model-invocation: true` is absent from the agent's skill listing entirely — 21 of the 36 in `.claude/skills/` are, including `grill-with-docs`, `to-spec`, `to-docs`, `to-tickets`, `implement`, `triage` and `wayfinder`. A slash command only expands when it starts the message, so a skill named mid-sentence or without its slash arrives as plain text naming a skill the agent can't see. **When the user names a skill you can't find in your listing, read `.claude/skills/<name>/SKILL.md` and follow it — never substitute a similarly-named visible skill.** `grill-with-docs` is `grilling` + `domain-modeling`; running only the first silently drops the glossary work. `.claude/skills/` is the copy Claude Code reads; `.agents/skills/` is a parallel copy for other harnesses and has already drifted from it.
