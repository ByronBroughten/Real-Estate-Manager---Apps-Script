# Claude instructions for this repo

Read `README.md` before making non-trivial changes — it explains the architecture, naming vocabulary, and generated-data boundaries this project depends on. Read `STYLE.md` before writing or refactoring TypeScript — code-shape rules (classes over function modules, getters over returned state bags, dead-code deletion) distilled from the user's own refactors of AI-generated code. The short version:

- **`src/00_*`–`06_API/` are a generic Sheets+Apps-Script framework; `src/businessEndpoints.ts`/`src/businessEndpointHandlers/` are the only place real-estate-specific logic belongs.** Dependencies only point downward by folder number — never import from a higher-numbered tier. `businessEndpoints.ts`/`businessEndpointHandlers/` sit outside the numbering (like `utils/`) and may import from any tier.
- **`02_SpreadsheetRaw`'s classes are raw-index Sheets API access only** — whole rows/columns by GID + index, sheet properties, and `UniformRowRaw`. They never resolve a column by name or `columnId`; that's `03_SpreadsheetIndexed`/`04_SpreadsheetNamed`'s job. The folder also holds `SpreadsheetSchema.ts` (next bullet), which does resolve columns — it lives there because it must sit below both tiers that use it, and Raw classes are limited to `SpreadsheetSchema` by convention, not by the import graph. Generating/updating `01_generatedConfigs` is a separate `05_Operators` tier's job (`SheetConfigOperator`/`ColumnConfigOperator`/`ValueConfigOperator`, coordinated by `ConfigOrchestrator`) — config maintenance is neither Raw's nor Named's responsibility.
- **Three schema classes, one accessor.** `SpreadsheetSchema`/`SheetSchema`/`ColumnSchema` all live in `src/02_SpreadsheetRaw/SpreadsheetSchema.ts` — one module, because they form an import cycle that would crash at Apps Script runtime if split. Every class that has a schema exposes it as `schema`, narrowed to its level (spreadsheet, sheet/row, or column/cell); `baseSchema`/`ssSchema`/`columnSchema`/`sheetSchema` are gone. Build one via `SheetSchema.fromSheetName`/`.fromSheetGid` or `ColumnSchema.fromColumnName`/`.fromColumnId` — name-addressed gets full literal precision, GID-addressed gets the widened default. `SheetSchema` and `ColumnSchema` are siblings, not parent and child. See README's "The schema classes".
- **Never run `clasp push`, `clasp run`, `clasp deploy`, `npm run build`, or `npm run gen:configs` without asking first.** They affect a live Apps Script deployment. `npm run gen:configs` doesn't just read — it writes to the live Sheet Config/Column Config sheets and to business sheets' header rows (missing column IDs), then atomically regenerates `sheetConfigs.ts`/`columnConfigs.ts`/`valueConfigs.ts` together, all three or none. Never run a partial/older regeneration path that updates a subset instead — see README.md's "Generated data" section for why. `npm run tsc` is always safe, as is `npx tsc --noEmit --extendedDiagnostics` for measuring type-check cost.
- **Verify a type-level claim with an identity check, not an assignment** — an assignment passes against `any` and against `never`, so it proves nothing about a mapped or conditional type. Use `IsExactly`/`assertType` from `src/testSupport/typeAssertions.ts`, and treat any probe that needed an `any` to compile as having proved nothing. See STYLE.md's "Type modeling" and README's "Type-check cost."
- **The `gsheets` MCP's read tools (`list_spreadsheets`, `list_sheets`, `get_sheet_data`) are always fine.** Any write tool (`create_spreadsheet`, `create_sheet`, `update_cells`, `batch_update_cells`) needs a stated specific plan — exact sheet/range/values, or exact new sheet/spreadsheet — and explicit permission first, not a general go-ahead. `share_spreadsheet` needs its own separate confirmation of exactly who and at what permission level, since it grants access rather than just changing data.
- **Don't hand-edit the generated data** in `sheetConfigs`/`columnConfigs`/`valueConfigs` (`src/01_generatedConfigs/`) — regenerate from the spreadsheet instead, per README. Exception: `sheetConfigs`/`columnConfigs` entries for the config-describing sheets themselves (`sheetConfig`, `columnConfig`, `spreadsheetConfig`, `valueConfig`) form a guaranteed floor and are meant to stay fixed rather than be regenerated away (see README).
- **An endpoint is one entry keyed by the column whose action-row checkbox triggers it** — any column, no suffix requirement. The entry's value is an object: a required `action`, plus optional `timeLastRan`, `runStatus` and `selector` column names, plus `runsOnUncheck`. Each key carries its own sheet, so the three column names are constrained to that sheet and to the value type each needs; a cross-sheet or wrongly-typed column is a compile error. Without `runsOnUncheck` the entry checkbox is a **run button** and clears itself on the run's setup flush; with it, the endpoint fires on tick *and* untick and the box is left alone. A declared `selector` column prunes the sheet to the ticked rows, and `timeLastRan`/`runStatus` are stamped into those rows (or into every table data row when there's no selector). `EndpointRun` owns all of that; `Api` only decodes the event and dispatches. Register endpoints with a plain `: Endpoints` annotation, never `makeStructuredConfig`, which silently accepts a key that isn't a real column. The three suffix strings in `spreadsheetConfig` are now **naming convention only** — nothing dispatches on them. See `CONTEXT.md` for what these words mean and README's "Endpoint dispatch" for how the dispatch is built.
- **A column is addressed either relatively (`<SN, CN>`) or absolutely (`ColumnFullName`), and there is deliberately no type-level bridge between them** — building one blows up the type-checker. Reach for the absolute family only when you need to name a *set* of columns cutting across sheets; everything sheet-scoped stays on `<SN, CN>`. See README's "Two ways to address a column".
- **Optimizing a trigger means removing a Sheets round trip — nothing else moves the number.** All API traffic funnels through `SpreadsheetRaw.fetchAllGathered`/`_sendUpdateRequests` (~250–450ms each); the framework's own CPU is ~20–60ms per run. `SpreadsheetApp` was measured as a cheaper alternative and is *slower*; don't re-propose it without new measurements. See README's "Round trips are the cost".
- **This code runs in Google Apps Script, not Node.** No Node/DOM APIs at runtime — only in build tooling.
- **Tests run on Vitest, safe to run freely.** `npm test` (or `npm run test:coverage`) never touches the live spreadsheet or Apps Script — everything it exercises runs against fakes. Co-locate a new test as `Foo.test.ts` next to `Foo.ts`; shared fakes for the ambient GAS globals (`Sheets`, `PropertiesService`, `ScriptApp`, `SpreadsheetApp`) live in `src/testSupport/`, outside the tier numbering like `utils/`. See README's "Testing" section for the mocking approach and what's covered so far. `npm run tsc` remains the whole *type*-verification story; run both before calling a change done.
- `src/businessEndpoints.ts` is live (wired into `triggerOnEdit` via `06_API`'s `Api` class), but the domain classes it will eventually call (`ChargeMgmt`, `ExpenseMgmt`, `LeaseMgmt`, `LedgerMgmt`, `PaymentMgmt`, `SubsidyMgmt`, in `src/businessEndpointHandlers/`) are still fully commented out, pre-reorg legacy awaiting reimplementation. None of this is broken — an expected state, and STYLE.md's commented-out-code exception applies here: ask before deleting or rewriting over these blocks.

Four prose files, four jobs. **README.md** is the map — what exists and where — and holds the **architecture** vocabulary (**Raw / Indexed / Named / Operator / Trait / Config / Schema**) under "Naming vocabulary". **CONTEXT.md** is the glossary of **domain** words (**endpoint / runner / two-way endpoint / selector / run status / run state**). **STYLE.md** is code shape. **DESIGN.md** is why the design is the way it is — read it before arguing that something looks missing or over-engineered; several of its principles exist specifically to stop a deliberate absence being helpfully filled in. Both vocabularies are used precisely; if you're placing or renaming a file and unsure which applies, ask rather than guess.

## Agent skills

### Issue tracker

Issues and specs live as GitHub issues in `ByronBroughten/Real-Estate-Manager---Apps-Script`, driven via the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

The five canonical triage roles, used verbatim as label strings. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: `CONTEXT.md` at the repo root, created lazily by `/domain-modeling`. **There is no `docs/adr/` tree, and none should be created** — DESIGN.md rules it out: specs are published as GitHub issues, and a second filing system would only drift from them. An architectural argument goes into DESIGN.md's principle list, cited by issue or commit. See `docs/agents/domain.md`.

### Hidden skills

A skill marked `disable-model-invocation: true` is absent from the agent's skill listing entirely — 21 of the 36 in `.claude/skills/` are, including `grill-with-docs`, `to-spec`, `to-docs`, `to-tickets`, `implement`, `triage` and `wayfinder`. A slash command only expands when it starts the message, so a skill named mid-sentence or without its slash arrives as plain text naming a skill the agent can't see. **When the user names a skill you can't find in your listing, read `.claude/skills/<name>/SKILL.md` and follow it — never substitute a similarly-named visible skill.** `grill-with-docs` is `grilling` + `domain-modeling`; running only the first silently drops the glossary work. `.claude/skills/` is the copy Claude Code reads; `.agents/skills/` is a parallel copy for other harnesses and has already drifted from it.
