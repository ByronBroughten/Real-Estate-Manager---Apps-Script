# Real Estate Manager — Apps Script

A Google Apps Script project (TypeScript, compiled and pushed via `clasp`) for managing real estate operations — properties, units, households, leases, subsidies, charges, and payments — on top of a Google Sheets spreadsheet that acts as the database and the UI.

## Two layers, one codebase

This repo is really two things stacked on top of each other:

- **`src/00_*` through `src/06_API/` are a project-agnostic framework** for building typed, structured apps on top of Google Sheets + Apps Script. The Raw tier talks to the Sheets Advanced API purely in terms of raw row/column indexes and sheet properties; the Indexed and Named tiers resolve the typed schema on top of that by index/name. A dedicated Operators tier (`05_Operators`) sits above Named and owns generating/updating `01_generatedConfigs` from the live "Sheet Config"/"Column Config"/"Value Config" sheets — maintaining generated data is neither Raw's nor Named's job. `06_API` sits on top as a generic endpoint-dispatch layer (`Api`, `EndpointRun`) that routes sheet-edit events to registered endpoints by column name. Nothing in these folders should reference real-estate concepts (properties, leases, tenants, etc.). If you're adding something reusable that any Sheets-backed app would want, it belongs here.
- **`src/businessEndpoints.ts` and `src/businessEndpoints/` are this specific project** — together the only place real-estate domain logic (charges, leases, subsidies, payments, ledgers) should live: `businessEndpoints.ts` holds the `endpoints` record passed into `06_API`'s `Api` class, and `businessEndpoints/` holds one file per endpoint, with `businessEndpoints/BusinessOperators/` for any classes they need. Everything here is built on top of the framework layers below it.

Keep that boundary in mind before adding a file: "would this make sense in a completely different Sheets-backed app?" If yes, it belongs in 00–06, generically named. If no, it belongs in `businessEndpoints/` — or, if it is a one-off maintenance job rather than something an operator triggers from the sheet, in `src/chores/` (see [Chores](./docs/architecture/chores.md)). `src/nodeHost/` is a third thing again: not a layer of the app but the adapter that lets the framework run somewhere other than Apps Script (see [How it runs](./docs/how-it-runs.md)).

## Architecture: the numbered tiers

Each top-level folder under `src/` is a dependency tier. **Rule: dependencies only point downward.** A file in tier `N` must never import from a tier numbered higher than `N`. When adding a file, put it in the lowest tier that satisfies what it actually needs — don't reach for a higher tier out of convenience.

| Folder                  | Tier role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | May import from  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `00_base`               | Zero-dependency primitives: `CellValue`/`CellValueName` types, base (non-config-dependent) value schemas, raw Apps Script service wrappers (`AppsScript.ts`), ambient GAS types.                                                                                                                                                                                                                                                                                                                                                                                                                                        | `utils/` only    |
| `01_generatedConfigs`   | The config data describing the spreadsheet's own structure — which sheets exist, their columns (by `columnId`, no longer by index), value-name enums, and the hand-authored layout constants (`spreadsheetConfig`) — plus the schema types built from that data. Includes a small hardcoded/bootstrap subset for the Sheet Config/Column Config sheets themselves. See [`docs/generated-data.md`](./docs/generated-data.md).                                                                                                                                                                                                                          | `00`             |
| `02_SpreadsheetRaw`     | Low-level, **config-independent** wrapper around the Sheets Advanced API: fetch/update whole rows and cells by sheet GID + row/column index, and fetch sheet properties. Includes `UniformRowRaw`, a structural row (header/columnId/footer) addressed by role name rather than by any generated schema. The Raw *classes* never resolve a column by name or column ID — see 03/04. The folder also owns the schema module (`SpreadsheetSchema`/`SheetSchema`/`ColumnSchema`), which must live below both tiers that consume it; `SheetSchema`/`ColumnSchema` do resolve columns, so Raw classes are held to `SpreadsheetSchema` by convention rather than by the import graph (see [schema classes](./docs/architecture/schema-classes.md)). | `00`, `01`       |
| `03_SpreadsheetIndexed` | Config-**dependent** classes that address sheets/columns by GID/index rather than by name (`SheetIndexed`, `ColumnIndexed`, `RowIndexed`, etc.). A column's index is resolved here at runtime — by looking up its `columnId` (from `01_generatedConfigs`) against the live "columnId" row fetched via `02`'s `UniformRowRaw` — rather than being stored in config data.                                                                                                                                                                                                                                       | `00`, `01`, `02` |
| `04_SpreadsheetNamed`   | Config-dependent, **name**-based API — the one most application code should use (`SheetNamed`, `ColumnNamed`, `RowNamed`, `CellNamed`).                                                                                                                                                                                                                                                                                                                                                                                                                                                            | `00`–`03`        |
| `05_Operators`          | Operators — classes built on a Named base that add methods suited to one data structure. Config maintenance is one family: `SheetConfigOperator`/`ColumnConfigOperator`/`ValueConfigOperator` each read one real Config sheet ("Sheet Config"/"Column Config"/"Value Config") by name and regenerate the matching tier-01 file, and `ConfigOrchestrator` coordinates all three into one atomic sync-then-regenerate flow; `GenericSheetOperator` is their shared base. `CheckboxColumnOperator` is the other kind — a column-scoped operator constrained to non-formula `checkbox` columns. Depends on `04_SpreadsheetNamed` since it reads sheets by name.                                                                                                                                                                              | `00`–`04`        |
| `06_API`                | Generic, config-independent-of-domain endpoint dispatch: `Api` decodes a sheet-edit event into a column's full name and looks it up in the endpoint map (see [endpoint dispatch](./docs/architecture/endpoint-dispatch.md)); `EndpointRun` owns everything after that — the selection, the run states, the try/catch and the two flushes — reporting each run's state back into the rows it is about. Still project-agnostic — takes its endpoint map as a parameter, so it has no real-estate knowledge itself.                                                                                                                                                                                                      | `00`–`05`        |

`src/businessEndpoints.ts` and `src/businessEndpoints/` sit outside the numbering (like `utils/`) as the real-estate domain logic for _this_ project — the only place allowed to know about properties, leases, tenants, etc. `businessEndpoints.ts` builds the endpoint map passed into `06_API`'s `Api` class; `businessEndpoints/` holds one file per endpoint, each exporting a single entry the registry wires to its key, and `businessEndpoints/BusinessOperators/` holds any classes those endpoints need. All may import from any tier. `src/index.ts` sits outside the numbering as the entry-point file Apps Script calls into.

`src/chores/` and `src/nodeHost/` sit outside the numbering for the same reason, and may import from any tier. `src/nodeHost/` is the Node host's type-checked, tested half — the adapter (`SheetsServiceNode`), the globals installer (`NodeHost`) and the preview renderer (`UpdateRequestSummary`) — and touches no Node API itself; the Node-specific half is `scripts/nodeHost.mjs` and `scripts/fetchSync.mjs`. `src/chores/` is the chores home (see [Chores](./docs/architecture/chores.md)). Both live under `src/` so `npm run tsc` covers them, and **nothing in `src/index.ts` imports either**, so `rollup` never ships them to the deployment and no build configuration changes to keep that true.

## Naming vocabulary

These are the **architecture** words — the layering vocabulary. The domain words an operator would recognise (endpoint, runner, two-way endpoint, selector, run status, run state) live in [`CONTEXT.md`](./CONTEXT.md) instead.

They are used precisely and consistently — don't use them loosely:

- **Raw** — depends on nothing generated from the spreadsheet's config sheets except `spreadsheetConfig` and sheet GIDs. If a *class* resolves a column by name or `columnId`, it is not "Raw," regardless of what folder it's in. Raw's job is raw-index Sheets API access only — fetching whole rows/columns and sheet properties. The schema module is the one thing in `02` that resolves columns, and only because it has to sit below its consumers; Raw classes get `SpreadsheetSchema` and nothing more.
- **Indexed** — config-dependent, addresses things by sheet GID / column index (not by name). A column's index isn't stored in config data; Indexed resolves it live from the column's `columnId` against the live "columnId" row.
- **Named** — config-dependent, addresses things by sheet name / column name.
- **Operator** — a class based on a Named base class that adds methods suited to one particular data structure, reaching its subject through a getter rather than inheriting it (see `docs/style/class-shape.md`). An Operator serving this project's own endpoints rather than the framework lives in `src/businessEndpoints/BusinessOperators/`, where `OccupancyLedgerOperator` is the first. Config maintenance is one family of Operators, not the definition: `SheetConfigOperator`/`ColumnConfigOperator`/`ValueConfigOperator` each read a real Config sheet by name and regenerate the matching tier-01 config file, and `ConfigOrchestrator` coordinates several into one flow. Maintaining generated data is an Operator-tier job, not Named's. `CheckboxColumnOperator` is the non-config kind — a column operator that can only be attached to a non-formula `checkbox` column.
- **Config** — the data describing the spreadsheet's own structure, generated (or eventually generated) from the real spreadsheet rather than freely made up. Lives in `01_generatedConfigs`. Naming has three tiers, from a full collection down to a single fact:
  - **`xConfigs`** (plural, e.g. `sheetConfigs`) — the whole map, one entry per sheet/column/value-name.
  - **`XConfig`** (singular, e.g. `SheetConfig`, `ColumnConfig`) — one entry's full record.
  - **trait** — one property picked out of a single config record (e.g. a sheet's `sheetGid`), via accessors like `getSheetTraitByGid`/`getColumnTraitByIndex`. The same word is reused one layer up for picking a single property out of a `ValueSchema` (`getValTrait`) — "trait" always means "one property of a multi-field record," never a collection.
  - `spreadsheetConfig` is the one exception to the plural/singular split: there's only one spreadsheet, so it's a single record with no separate `spreadsheetConfigs` collection.
  - `sheetConfigs`/`columnConfigs`'s own entries for the four config-describing sheets — `sheetConfig`, `columnConfig`, `spreadsheetConfig`, and `valueConfig` — are guaranteed to always come out the same on regeneration, forming a fixed floor underneath the generation process itself (it needs a fixed way to find those sheets and their own columns before it can generate anything else). Treat that floor as guaranteed, not as data to "fix" by trying to regenerate it away.
- **Meta / primary** — an **axis orthogonal to the tiers**, not a fourth tier. Every tier's sheets and columns come in two views: the **primary** view deals in the structure's contents (data rows, data columns, data cells) and takes the **unmarked** name; the **Meta** view is the structure seen as its own shape (header row, action row, column IDs, a column's sampled traits) and takes a `Meta` stem — `SheetRaw`/`SheetMetaRaw`, `ColumnNamed`/`ColumnMetaNamed`, and so on. Cells, spreadsheets and uniform rows have no such split and gain none; a uniform row is not a Meta form, it is a row that physically holds the columns' metadata.
  - **Navigation.** Each view's plain nouns mean that view's classes: a sheet's `column(name)` and a column's `sheet` stay within the view you are already in. Crossing takes exactly one word — `meta` from primary to Meta, `primary` from Meta to primary — and there is no cross-level shortcut: a Meta sheet from a column is `column.meta.sheet`, a Meta column from a sheet is `sheet.meta.column(name)` or `sheet.column(name).meta`. From the spreadsheet, `sheet(name)` yields the primary sheet and `sheetMeta(name)` the Meta one, at every tier.
  - **Which class does a member belong to?** A member belongs on the Meta class if it **only** (1) acts on or reads from a uniform row, (2) samples the top data row to derive a column-wide fact, or (3) reads column-wide structure from the table's own column properties. Everything else defers to the primary class. A uniform row used as an incidental *mechanism* rather than as the member's subject does not qualify — the sheet-properties fetch touches the header row only as a probe to make the API return table metadata, and stays primary. Criterion 3 exists because 1 and 2 do not cover a column's data-validation strings or its declared column type, whose only consumer is on the Meta side.
  - Members both sheet views genuinely use live on the tier's shared abstract sheet class instead (see [class chains](./docs/architecture/class-chains.md)).
- **Active facts** — the column-wide facts sampled from a column's top data row: whether the column is a formula, its number format type, and its top value. They keep the `active` prefix in the sense above — as the sheet currently stands — and live on the Meta column, which is criterion 2 of the Meta/primary split. Two writers fill them and neither overwrites the other: `SheetRaw`'s integration walk records them for the table columns the payload described, because whether a cell holds a formula and what its number format is exist only while the payload is in hand; `SpreadsheetRaw`'s finalize pass then *ensures* them, blank, for the table columns it did not (#17). Only table columns ever get them, since every consumer reaches one through a column ID and column IDs live only inside the table.
- **Schema** — type/validation logic layered on top of Config data. Two unrelated families share the word: the spreadsheet schema (`SpreadsheetSchema`/`SheetSchema`/`ColumnSchema`, see [schema classes](./docs/architecture/schema-classes.md)) and the value schema (`ValueSchema`, for validating a single cell's value). **Nearly every cell is tri-state: `Value<VN>` includes `""`** — a `boolean` column reads `boolean | ""`, a `number` column `number | ""` — because an untouched cell is empty, not defaulted. The one exception is `checkbox`, whose value type is exactly `boolean` (#12); don't restore the blank to it. Code that branches on a column's value has to say what empty means rather than assuming the base type.
  - **Three words, and the column decides what the unmarked one means.** `valueNotEmpty` excludes `""` from the return type and throws when the cell is blank, always, on every column; `valueOrEmpty` is the same read with `""` still in the union, for a caller that has decided what blank means; `value` is whichever of the two the column's own **Empty value allowed** box declares (#13) — blank-excluding when the box is unticked, blank-tolerant when it is ticked. The plurals follow the same rule — `valueArrNotEmpty` throws, `valueArrOrEmpty` doesn't, `valueArrFilterEmpty` drops the blanks, and `valueArr` is what the column declared. Only Named can see a declaration, so only Named offers `value`/`valueArr`: Indexed resolves columns by generated id and exposes `valueNotEmpty`/`valueArrNotEmpty` plus the blank-tolerant pair, and Raw declines both marked-strict and unmarked words because validation isn't its job — `CellRaw`/`ColumnRaw`/`RowRaw`/`UniformRowRaw` expose `valueOrEmpty`/`valueArrOrEmpty` and nothing shorter. After that split each word means one thing at every tier it exists on. The suffix marks the *empty* axis only — every form still throws on an inactive cell, which is the separate "fetched into local state, not present on the sheet" condition. `CellNamed` runs its own blank check rather than delegating to Indexed's, so the message names the sheet and column the caller actually wrote instead of a generated column id (#8). **`RowNamed.blankRequiredColumnNames` asks the same declaration a different question** — which of the columns the row actually holds are blank and don't allow it — so an endpoint reporting on missing values reads the sheet's own record of mandatoriness rather than keeping a list of its own (#23). A column whose blank reads as a real value is never among them: a checkbox's blank is `false`, which is an answer, not a hole.
  - **The checkbox was the trap, and declaring the column type is what disarms it.** A column whose type menu says Checkbox gets the `checkbox` value name, whose value type is exactly `boolean` and whose blank reads as `false`, so `column.value(rowIndex) === true` over a selector column is a plain comparison. The coercion is a `blankReadsAs` field on the value schema, applied by `CellIndexed.valueOrEmpty` — the lowest tier that knows a cell's value name — so Indexed and Named agree and Raw still reports the wire. A column left on Automatic that merely *holds* `TRUE` keeps the `boolean` value name, keeps its blank, and keeps counting toward the untyped tally; the trap is still live there, and so it is for every drift check against a config sheet, where the blank *is* the drift being detected. Writes go the other way regardless: the framework unticks by writing an explicit `false` rather than clearing the cell (`ColumnMetaNamed.actionRowToDefault`, `CheckboxColumnOperator.uncheckActiveCells`).
  - **An in-app date is a `DateSerial` — a whole-day Sheets serial — never a JS `Date`.** A `date` column's `value` is a count of whole days from the Sheets epoch, branded at the type level so a rent or a count can't be passed where a date is wanted (#15). `Dat` is the calendar-day module and its interface is serials in, serials out: build one with `Dat.fromYmd` or `Dat.today`, move by `Dat.addDays`/`addMonths` rather than `+ 1` (which widens back to `number` and drops the brand), and don't convert to `Date` at the read line — `serialToDate`/`dateToSerial` are gone, and the whole-day rule lives in one place, `Dat.isSerial` — `Dat.validate` is its throwing form, and `Val.is.date`/`Val.validate.date` check through that same guard rather than restating it. `Tim` is the separate datetime module, still speaking `Date` and borrowing timezone, epoch and day length from `Dat`. The blank is untouched: a blank date cell still reads `""` through `valueOrEmpty` and still throws through the strict words.
  - **`emptyValueAllowed` reaches the read path, and shapes the accessor rather than the value type.** It used to be deliberately unwired, on the grounds that the trait asks whether the *column* may hold a blank while the accessor asks whether this *call site* handles one. That held while the trait changed nothing about a read; it stopped holding once the goal was for `value` to be the right call on most columns, so the column's declaration now decides (#13). The trait cannot narrow `ColumnValue` and does not try: clearing a row writes a blank into every non-formula column, unticked ones included, so a blank genuinely can sit there. Note the asymmetry with `checkbox` above — that one is a fact about a type, this one is a promise a throw enforces for the duration of one call. Enforcement stays at access and never at fetch: a sweep over fetched cells would fire on the blank row, on every freshly appended row and on any column whose value name defaults to a blank, and would kill a run over a column nothing read. The write path is unchanged, since tightening writes against the trait would make the blank row unconstructible.

If you're renaming or relocating something and unsure which word applies, ask rather than guess — these distinctions were deliberately hashed out and folder placement depends on them.

## Generated data — do not hand-edit

**Never read `columnConfigs.ts` whole** (~5k lines). `sheetConfigs.ts` is the sheet list. Grep `columnConfigs.ts` for the sheet key (`"occupancy":`) and read that object only.

## Known rough edges

- **The properties probe is blind to a Table that moved down or right.** On the trigger path, a sheet's table metadata arrives only because `SheetRaw.gatherFetchProperties` requests the single cell at the configured header row and start column, and the Sheets API returns a sheet's `tables` only for a filter whose range overlaps the table. That probe is built from the two constants the table-placement check compares against, so a table that moved down or right returns no metadata at all and looks identical to a table that was never created. That is why `SpreadsheetRaw`'s placement reporter pays for one full sheet-properties read before throwing, to tell "no Table here" from "Table somewhere else" — only on a path that is already aborting (#9).
- **Table column properties are keyed absolutely but read table-relatively.** `SheetRawBase._parseColumnProperties` stores `columnValidationValues` and `columnDeclaredTypes` by absolute column index, falling back to `startColumnIndex + offset` when the API omits `columnIndex`. The API states that index table-relative, so the two branches agree only while the table starts at column 0. Nothing is wrong today because it always does, but a table starting elsewhere would silently mis-key every declared column type.
