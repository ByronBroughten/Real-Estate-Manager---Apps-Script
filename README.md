# Real Estate Manager — Apps Script

A Google Apps Script project (TypeScript, compiled and pushed via `clasp`) for managing real estate operations — properties, units, households, leases, subsidies, charges, and payments — on top of a Google Sheets spreadsheet that acts as the database and the UI.

## Two layers, one codebase

This repo is really two things stacked on top of each other:

- **`src/00_*` through `src/06_API/` are a project-agnostic framework** for building typed, structured apps on top of Google Sheets + Apps Script. The Raw tier talks to a host-neutral `RawSource` in terms of raw row/column indexes and sheet properties (`GoogleSheetsAPI` is the Google implementer); the Identified and Named tiers resolve the typed schema on top of that by generated ID and by name. A dedicated Operators tier (`05_Operators`) sits above Named and owns generating/updating `01_SpreadsheetSchema/generated/` from the live Spreadsheet Config/Sheet Config/Column Config/Value Config sheets — maintaining generated data is neither Raw's nor Named's job. `06_API` sits on top as a generic endpoint-dispatch layer (`Api`, `EndpointRun`) that routes sheet-edit events to registered endpoints by column name. Nothing in these folders should reference real-estate concepts (properties, leases, tenants, etc.). If you're adding something reusable that any Sheets-backed app would want, it belongs here.
- **`src/businessEndpoints.ts` and `src/businessEndpoints/` are this specific project** — together the only place real-estate domain logic (charges, leases, subsidies, payments, ledgers) should live: `businessEndpoints.ts` holds the `endpoints` record passed into `06_API`'s `Api` class, and `businessEndpoints/` holds one file per endpoint, with `businessEndpoints/BusinessOperators/` for any classes they need. Everything here is built on top of the framework layers below it.

Keep that boundary in mind before adding a file: "would this make sense in a completely different Sheets-backed app?" If yes, it belongs in 00–06, generically named. If no, it belongs in `businessEndpoints/` — or, if it is a one-off maintenance job rather than something an operator triggers from the sheet, in `src/chores/` (see [Chores](./docs/architecture/chores.md)). `src/nodeHost/` is a third thing again: not a layer of the app but the adapter that lets the framework run somewhere other than Apps Script (see [How it runs](./docs/how-it-runs.md)).

## Architecture: the numbered tiers

Each top-level folder under `src/` is a dependency tier. **Rule: dependencies only point downward.** A file in tier `N` must never import from a tier numbered higher than `N`. When adding a file, put it in the lowest tier that satisfies what it actually needs — don't reach for a higher tier out of convenience.

All may import from any tier. `src/index.ts` sits outside the numbering as the entry-point file Apps Script calls into.

`src/chores/` and `src/nodeHost/` sit outside the numbering for the same reason, and may import from any tier. `src/nodeHost/` is the Node host's type-checked, tested half — `NodeHost` constructs `GoogleSheetsAPI` with the HTTP transport and installs PropertiesService and Logger, plus the preview renderer (`UpdateRequestSummary`) — and touches no Node API itself; the Node-specific half is `scripts/nodeHost.mjs` and `scripts/fetchSync.mjs`. `src/chores/` is the chores home (see [Chores](./docs/architecture/chores.md)). Both live under `src/` so `npm run tsc` covers them, and **nothing in `src/index.ts` imports either**, so `rollup` never ships them to the deployment and no build configuration changes to keep that true.

## Naming vocabulary

These are the **architecture** words — the layering vocabulary. The domain words an operator would recognise (endpoint, runner, two-way endpoint, selector, run status, run state) live in [`CONTEXT.md`](./CONTEXT.md) instead.

They are used precisely and consistently — don't use them loosely:

- **Source** — the tier below everything that knows this spreadsheet: the `RawSource` port, its Google adapter, the Apps Script wrappers, and the cell values that cross the port.
- **Raw** — positional. It addresses sheets, rows and cells by GID and index, knows the layout and sheet list through `SpreadsheetBaseSchema` and `SpreadsheetSchema`, and never resolves a column by name or `columnId`; a lint rule holds Raw files to that. Raw's job is positional spreadsheet access only — fetching whole rows/columns and sheet properties through `RawSource`.
- **Identified** — addresses a column by generated identity (sheet GID + column ID), knows each column's config (value name, default, blank coercion), and types values by the value-name union. A column's index isn't stored in config data; Identified resolves it live from the column's `columnId` against the live "columnId" row.
- **Named** — config-dependent, addresses things by sheet name / column name.
- **Tier word** — every tier class name ends in its tier word: state types (`StateRaw`, `SheetStateIdentified`), bases (`SpreadsheetBaseRaw`, `SheetBaseNamed`) and Common classes (`SheetCommonIdentified`) alike. Each of the Raw, Identified and Named tiers keeps its bases and Common classes in `ClassBases/`. A tier root is named `<Scope>Base<Tier>` (`SpreadsheetBaseSchema`, `SpreadsheetBaseRaw`, `SpreadsheetBaseOperator`), and the rule has no exceptions: the schema classes end in `Schema`.
- **State** — members are named by scope (`sheetState`, `rowState`), and end in the tier word too where one instance holds more than one tier's state at that scope, so they read as their type (`StateRaw` → `spreadsheetStateRaw`, `StateIdentified` → `spreadsheetStateIdentified`). `RawSource` is a port in the Source tier, not a Raw-tier type.
- **Base** — a class root (`<Scope>Base<Tier>`, `ValueSchemaBase`) or an index origin (`Base0`/`Base1`), and nothing else. What the framework supplies whatever the spreadsheet adds is **Framework** (`frameworkValueNames`, `frameworkEndpoints`).
- **Operator** — a class based on a Named base class that adds methods suited to one particular data structure, reaching its subject through a getter rather than inheriting it (see `docs/style/class-shape.md`). An Operator serving this project's own endpoints rather than the framework lives in `src/businessEndpoints/BusinessOperators/`, where `OccupancyLedgerOperator` and `PropertyExpenseOperator` are the two. Config maintenance is one family of Operators, not the definition: `SpreadsheetConfigOperator`/`SheetConfigOperator`/`ColumnConfigOperator`/`ValueConfigOperator` each read a real Config sheet by name and regenerate the matching tier-01 config file, `ConfigOrchestrator` coordinates several into one flow after running the config-sheet floor, and `ConfigSheetFloor` declares the live edit warnings on the config-sheet floor and sets floor columns back to their seeded types. Maintaining generated data is an Operator-tier job, not Named's. `CheckboxColumnOperator` and `RowIdByNameOperator` are the non-config kind — column operators, the one attachable only to a non-formula `checkbox` column, the other resolving a name to a row id and filling a blank id on the row it resolved (#24).
- **Collaborator** — a class a coordinator builds from its own props and reaches through a lazy getter, holding one group of the coordinator's former private helpers. It extends the tier's Base class, is named `<Subject><Role><Tier>` (`SpreadsheetFetcherRaw`, `SpreadsheetFlusherRaw`, `SpreadsheetTableValidatorRaw`), and lives in a subfolder named after its coordinator (`02_SpreadsheetRaw/SpreadsheetRaw/`). Callers use the coordinator, never the collaborator. See `docs/style/class-shape.md`.
- **Config** — the data describing the spreadsheet's own structure, generated from the real spreadsheet rather than freely made up. Lives in `01_SpreadsheetSchema/generated/`. Naming has three tiers, from a full collection down to a single fact:
  - **`xConfigs`** (plural, e.g. `sheetConfigs`) — the whole map, one entry per sheet/column/value-name.
  - **`XConfig`** (singular, e.g. `SheetConfig`, `ColumnConfig`) — one entry's full record.
  - **trait** — one property picked out of a single config record (e.g. a sheet's `sheetGid`), via accessors like `getSheetTraitByGid`/`getColumnTraitById`. The same word is reused one layer up for picking a single property out of a `ValueSchema` (`getValTrait`) — "trait" always means "one property of a multi-field record," never a collection.
  - `spreadsheetConfig` is the one exception to the plural/singular split: there's only one spreadsheet, so it's a single record with no separate `spreadsheetConfigs` collection.
  - `sheetConfigs`/`columnConfigs`'s own entries for the four config-describing sheets — `sheetConfig`, `columnConfig`, `spreadsheetConfig`, and `valueConfig` — are guaranteed to always come out the same on regeneration, forming a fixed floor underneath the generation process itself (it needs a fixed way to find those sheets and their own columns before it can generate anything else). Treat that floor as guaranteed, not as data to "fix" by trying to regenerate it away.
- **Meta / primary** — an **axis orthogonal to the tiers**, not a fourth tier. Every tier's sheets and columns come in two views: the **primary** view deals in the structure's contents (data rows, data columns, data cells) and takes the **unmarked** name; the **Meta** view is the structure seen as its own shape (Table header row, action row, column IDs, a column's sampled traits) and takes a `Meta` stem — `SheetRaw`/`SheetMetaRaw`, `ColumnNamed`/`ColumnMetaNamed`, and so on. Cells, spreadsheets and uniform rows have no such split and gain none; a uniform row is not a Meta form, it is a row that physically holds the columns' metadata.
  - **Navigation.** Each view's plain nouns mean that view's classes: a sheet's `column(name)` and a column's `sheet` stay within the view you are already in. Crossing takes exactly one word — `meta` from primary to Meta, `primary` from Meta to primary — and there is no cross-level shortcut: a Meta sheet from a column is `column.meta.sheet`, a Meta column from a sheet is `sheet.meta.column(name)` or `sheet.column(name).meta`. From the spreadsheet, `sheet(name)` yields the primary sheet and `sheetMeta(name)` the Meta one, at every tier.
  - **Which class does a member belong to?** A member belongs on the Meta class if it **only** (1) acts on or reads from a uniform row, (2) samples the top data row to derive a column-wide fact, or (3) reads column-wide structure from the table's own column properties. Everything else defers to the primary class. A uniform row used as an incidental *mechanism* rather than as the member's subject does not qualify — the sheet-properties fetch touches the Table header row only as a probe to make the API return table metadata, and stays primary. Criterion 3 exists because 1 and 2 do not cover a column's data-validation strings or its declared column type, whose only consumer is on the Meta side.
  - Members both sheet views genuinely use live on the tier's shared abstract sheet class instead (see [class chains](./docs/architecture/class-chains.md)).
- **Active** — present in the working view, with row indexes still at their pre-flush positions. Not "exists on the sheet". On the `triggerOnEdit` path only the columnId row is ever fetched, so no data row is active — `rowIndexesFull`, derived from the table bounds, is what names every data row.
- **Active facts** — the column-wide facts sampled from a column's top data row: whether the column is a formula, its number format type, and its top value. They keep the `active` prefix in the sense above — present in the working view, indexes at pre-flush positions — and live in `ColumnStateRaw`, reached from the Meta column, which is criterion 2 of the Meta/primary split. Two writers fill them and neither overwrites the other: `SheetRaw`'s integration walk records them for the table columns the payload described, because whether a cell holds a formula and what its number format is exist only while the payload is in hand; `SpreadsheetRaw`'s finalize pass then *ensures* them, blank, for the table columns it did not (#17). Only table columns ever get them, since every consumer reaches one through a column ID and column IDs live only inside the table.
- **Schema** — type/validation logic layered on top of Config data. The Schema tier (`01_SpreadsheetSchema`) is everything that reads the generated configs, and it sits below Raw because Raw reads the layout and sheet list from it. Two unrelated families share the word: the spreadsheet schema (`SpreadsheetBaseSchema`/`SpreadsheetSchema`/`SheetSchema`/`ColumnSchema`, see [schema classes](./docs/architecture/schema-classes.md)) and the value schema (`ValueSchema`, for validating a single cell's value). **Nearly every cell is tri-state: `Value<VN>` includes `""`** — a `boolean` column reads `boolean | ""`, a `number` column `number | ""` — because an untouched cell is empty, not defaulted. The one exception is `checkbox`, whose value type is exactly `boolean` (#12); don't restore the blank to it. Code that branches on a column's value has to say what empty means rather than assuming the base type.
  - **Three words, and the column decides what the unmarked one means.** `valueNotEmpty` excludes `""` from the return type and throws when the cell is blank, always, on every column; `valueOrEmpty` is the same read with `""` still in the union, for a caller that has decided what blank means; `value` is whichever of the two the column's own **Empty value allowed** box declares (#13) — blank-excluding when the box is unticked, blank-tolerant when it is ticked. The plurals follow the same rule — `valueArrNotEmpty` throws, `valueArrOrEmpty` doesn't, `valueArrFilterEmpty` drops the blanks, and `valueArr` is what the column declared. Only Named can see a declaration, so only Named offers `value`/`valueArr`: Identified resolves columns by generated id and exposes `valueNotEmpty`/`valueArrNotEmpty` plus the blank-tolerant pair, and Raw declines both marked-strict and unmarked words because validation isn't its job — `CellRaw`/`ColumnRaw`/`RowRaw`/`UniformRowRaw` expose `valueOrEmpty`/`valueArrOrEmpty` and nothing shorter. After that split each word means one thing at every tier it exists on. The suffix marks the *empty* axis only — every form still throws on an inactive cell, which is the separate condition of a cell absent from the working view, whether or not it exists on the sheet. `CellNamed` runs its own blank check rather than delegating to Identified's, so the message names the sheet and column the caller actually wrote instead of a generated column id (#8). **`RowNamed.blankRequiredColumnNames` asks the same declaration a different question** — which of the columns the row actually holds are blank and don't allow it — so an endpoint reporting on missing values reads the sheet's own record of mandatoriness rather than keeping a list of its own (#23). A column whose blank reads as a real value is never among them: a checkbox's blank is `false`, which is an answer, not a hole.
  - **The checkbox was the trap, and declaring the column type is what disarms it.** A column whose type menu says Checkbox gets the `checkbox` value name, whose value type is exactly `boolean` and whose blank reads as `false`, so `column.value(rowIndex) === true` over a selector column is a plain comparison. The coercion is a `blankReadsAs` field on the value schema, applied by `CellIdentified.valueOrEmpty` — the lowest tier that knows a cell's value name — so Identified and Named agree and Raw still reports the wire. A column left on Automatic that merely *holds* `TRUE` keeps the `boolean` value name, keeps its blank, and keeps counting toward the untyped tally; the trap is still live there, and so it is for every drift check against a config sheet, where the blank *is* the drift being detected. Writes go the other way regardless: the framework unticks by writing an explicit `false` rather than clearing the cell (`ColumnMetaNamed.actionRowToDefault`, `CheckboxColumnOperator.uncheckActiveCells`).
  - **An in-app date is a `DateSerial` — a whole-day Sheets serial — never a JS `Date`.** A `date` column's `value` is a count of whole days from the Sheets epoch, branded at the type level so a rent or a count can't be passed where a date is wanted (#15). `Dat` is the calendar-day module and its interface is serials in, serials out: build one with `Dat.fromYmd` or `Dat.today`, move by `Dat.addDays`/`addMonths` rather than `+ 1` (which widens back to `number` and drops the brand), and don't convert to `Date` at the read line — `serialToDate`/`dateToSerial` are gone, and the whole-day rule lives in one place, `Dat.isSerial` — `Dat.validate` is its throwing form, and `Val.is.date`/`Val.validate.date` check through that same guard rather than restating it. `Tim` is the separate datetime module, still speaking `Date` and borrowing timezone, epoch and day length from `Dat`. The blank is untouched: a blank date cell still reads `""` through `valueOrEmpty` and still throws through the strict words.
  - **`emptyValueAllowed` reaches the read path, and shapes the accessor rather than the value type.** It used to be deliberately unwired, on the grounds that the trait asks whether the *column* may hold a blank while the accessor asks whether this *call site* handles one. That held while the trait changed nothing about a read; it stopped holding once the goal was for `value` to be the right call on most columns, so the column's declaration now decides (#13). The trait cannot narrow `ColumnValue` and does not try: clearing a row writes a blank into every non-formula column, unticked ones included, so a blank genuinely can sit there. Note the asymmetry with `checkbox` above — that one is a fact about a type, this one is a promise a throw enforces for the duration of one call. Enforcement stays at access and never at fetch: a sweep over fetched cells would fire on the blank row, on every freshly appended row and on any column whose value name defaults to a blank, and would kill a run over a column nothing read. The write path is unchanged, since tightening writes against the trait would make the blank row unconstructible.

If you're renaming or relocating something and unsure which word applies, ask rather than guess — these distinctions were deliberately hashed out and folder placement depends on them.

## Known rough edges

- **The properties probe is blind to a Table that moved down or right.** On the trigger path, a sheet's table metadata arrives only because `SheetRaw.gatherFetchProperties` requests the single cell at the Table header row and start column, and the Sheets API returns a sheet's `tables` only for a filter whose range overlaps the table. That probe, and the column-id row that shares its round trip, aim at the layout constant; later row fetches use the live Table start once `tables.range` is in state. A table that moved down or right still returns no metadata and looks identical to a table that was never created. That is why `SpreadsheetRaw`'s placement reporter pays for one full sheet-properties read before throwing, to tell "no Table here" from "Table somewhere else" — only on a path that is already aborting (#9).
- **Table column properties are keyed absolutely but read table-relatively.** `SheetBaseRaw._parseColumnProperties` stores validation values, condition types and declared types on `ColumnStateRaw` by absolute column index, falling back to `startColumnIndex + offset` when the API omits `columnIndex`. The API states that index table-relative, so the two branches agree only while the table starts at column 0. Nothing is wrong today because it always does, but a table starting elsewhere would silently mis-key every declared column type.
