# Queued writes and shared state

Map fragment. Sibling headings live in this folder.


Each tier's state has three groups. The **working** view is what the run sees: the fetched sheet plus every queued write, with row indexes at their pre-flush positions. The **fetch queue** is what the next read will fetch, and the **write queue** is what the next flush will send.

- **Raw spreadsheet:** `fetchQueue.gridRanges` for the next `fetchAllGathered`, and `writeQueue.updateRequests`, the requests a flush sends. The update requests stay spreadsheet-wide because the flush orders them by request kind across sheets.
- **Raw sheet:** `working` holds the title, known Table, rows, column states, conditional formats and edit protections. `fetchQueue` holds the gather flags for conditional formats and edit protections, plus `toFinalize`, the rows, columns and cells a fetch has filled but not yet finalized. `writeQueue` holds `sheet` (fills, sorts, column inserts), `rows` (each row's queued append, delete and cell updates, keyed by row index) and the row indexes an append has already handed out.
- **Identified sheet:** a `fetchQueue` only: fetch targets addressed by column ID and tagged by `kind`, plus gather flags that it passes down to Raw when it gathers the fetch.

`update`/`append`/`delete` don't hit the API — they mutate the working view and register the change on that sheet's `writeQueue`. Nothing reaches the spreadsheet until `batchUpdateGSheets()` turns each sheet's queued changes into update requests and `RawSource.flush` sends them. `GoogleSheetsAPI` maps each local operation onto Google request kinds (`updateCells`, `pasteData`, `repeatCell`, `appendCells`, …) and one `batchUpdate`.

Within a flush the requests go out in a fixed order: appends, column inserts, fills, per-cell updates, find-and-replaces, row deletes highest-index-first, then sorts, then conditional-format deletes highest-index-first, then conditional-format adds, then edit-protection deletes, then edit-protection adds, then raw. Appends therefore land **before** the deletes queued beside them, and same-sheet deletes go descending because each one shifts the rows beneath it. Conditional-format deletes use the same descending-index reason as row deletes: each removal renumbers the rules beneath it. Adds follow those deletes so a remove-then-re-add in one flush lands in the order it was queued. Edit-protection deletes are by id, so they do not need descending order. After row deletes are sent, that sheet's **row indexes** are **stale**. Both axes use that word: the row flag is a boolean (`rowIndexesAreStale`); column stale stays a watermark (`firstStaleColIndex`). A flush that added or deleted a conditional format rule sets a third per-sheet flag (`conditionalFormats.isStale`); a second rule-mutating flush against that sheet is refused until a refetch of its rules clears it. A flush that added or deleted an edit protection sets a fourth (`editProtections.isStale`); reading or mutating that sheet's protections is refused until a refetch. Every queue-time write whose flushed request will embed a row coordinate — `updateCells` range, `repeatCell` range, `pasteData` `coordinate.rowIndex`, row `deleteDimension`, both conditional-format rule operations, and a protection whose range or unprotected ranges carry row coordinates read off the sheet — throws because the method's **first line** called `this.sheet.activeTable.assertRowIndexesNotStale()` (or the equivalent on `ActiveTableRaw`). A whole-column protection is exempt from that row check and instead calls `validateColIndexNotStale` on its column index. A whole-sheet protection with no unprotected ranges is exempt from both. A new write method ships that assert in the same change; a method that only happens to read `endRowIndex` is not gated. `endRowIndex` still throws; the rest of the table object (column range, declared types, validation values, validation condition types) stays readable. Integrating sheet properties afterwards replaces the stored Table range and column properties from the payload but does **not** clear row-index stale — `clearRowIndexStale` is the only restore, unused in production, and nothing in fetch or integrate calls it. Reads by row index stay allowed and may lie. Hybrid cache after a partial refetch, a cross-sheet copy, and content-addressed find/replace are how a lying read can still damage integrity; a later restore without clearing local row state is unsafe. A column insert **not** at the Table end marks column indexes at and to the right of the insert stale; writes at those indexes throw, naming the first stale column index, while reads do not consult that watermark. An insert at the live Table end only grows the exclusive end column. The two stale axes are separate: a column insert does not stale row indexes, and a flushed row delete does not stale column indexes. Rule-index stale is the third and protection-list stale the fourth, and both are independent of the row and column axes. A table's `appendCells` requests collapse into **one request per sheet**, with a `rows` entry per appended row: Sheets' table-aware append targets the same first free row for every request in the batch, so N separate one-row appends only grow the table by one while the per-cell updates still land on the rows beneath it.

Most writes queue per cell and flush as one `updateCells` request each; a cell's queued entry holds an optional value, an optional formula, and an optional background colour (`RgbColor` in the Source tier, mapped to Google `Color` only inside `GoogleSheetsAPI`), merged across writes, so a value and a colour on one cell still cost one request and neither can cancel the other. A value and a formula are mutually exclusive on that same entry: writing one drops the other. Each request's field mask is built from what that entry actually holds, so a colour-only write can't blank the cell's value and a value-only write can't blank its colour — which is how a per-cell message written over a column-wide fill keeps the fill's colour unless it names its own. A column write instead queues one sheet-level *fill* per contiguous run of rows: `updateAllCells` fills every table data row of a column in one `repeatCell`, and `updateActiveCells` fills only the column's active rows, so stamping a selection costs no more requests than the selection is wide. `updateAllFormulas` / `updateActiveFormulas` are the formula-column siblings of those fills, and `updateFormula` is the per-cell sibling of `updateValue`. Both are exposed from `ColumnRaw`/`CellRaw` up through Identified and Named under the same names. Named type-restricts the three formula methods to formula columns; Identified runtime-refuses a formula write on a non-formula column; `GoogleSheetsAPI` serializes a string that already starts with `=` as `pasteData` with `PASTE_FORMULA` (RFC4180-quoted fields, tab delimiter, identical text on every row of a fill) and does not consult `isFormula`. Colour on the same change still serializes as today's `repeatCell` / `updateCells` colour path, so a formula-plus-colour flush is two requests in one `batchUpdate`. A formula string that does not start with `=` throws before anything is queued — the `=` is not prepended. A formula write does not mirror into local cell state, so a later read in the same run still sees the old effective value (colour-only writes are the precedent). Two consequences are invisible at the call site: fills are ordered **before** per-cell updates within a flush, so a per-cell write on a filled column wins regardless of which was queued first; and a fill's last row is snapshotted when queued, so it never reaches a row appended after it. State is still mirrored row by row for *value* fills — only the request collapses. `updateAllCells` and `updateAllFormulas` throw on a sheet that `SheetRaw.removeRowsExcept` has pruned to a selection, since a whole-column fill ignores active rows and would reach exactly the rows the prune excluded.

That `spreadsheetStateRaw` is threaded **by reference** through `spreadsheetNamedProps` into every collaborator getter, so an endpoint, its `ConfigOrchestrator`, and every operator beneath it all share one queue. A flush therefore commits everything queued anywhere in the run, not just what the calling object queued — which is why a failure path must `discardQueuedChanges()` before writing status, or the `finally` flush ships a half-finished sync. Discarding resets both write queues as groups (the spreadsheet's `updateRequests` and every sheet's `writeQueue`) rather than re-initializing individual fields. It leaves the working view reflecting writes that never happened, so it's a terminal step only.

**`findReplace` is the one write that names no coordinates, and it pays for that by invalidating every read.** It carries Google's own fields — `find`, `replacement`, `matchCase`, `matchEntireCell`, `searchByRegex`, `includeFormulas` — and a scope of a range, a sheet, or the whole spreadsheet, so `ColumnNamed`/`SheetNamed` build the scope while both strings stay plain: the value config governs neither, because Google matches the cell's text. It rides the same queue and the same dry run, and sits **after** per-cell updates because it reads the text as it stands mid-batch, so text queued beside it must land first. Two consequences follow from matching by content. Nothing can be mirrored into local state, since what matched is unknowable locally, so the flush marks **every** sheet's fetched cells stale — one rule rather than a scope-dependent one — and a read afterwards throws naming the findReplace until the next fetch clears it. A coordinate formula write (`updateFormula` / `updateAllFormulas` / `updateActiveFormulas`) is the other formula touch: it stamps a new formula onto a formula column by cell or fill as `pasteData` / `PASTE_FORMULA`, so Sheets runs the UI parser (table references included) rather than storing an unparsed `formulaValue`, and it does not invalidate reads. Colour may ride beside that paste in the same `batchUpdate`. `includeFormulas` remains the text-level rewrite of a formula already in place. `validateDataNotFormula` still refuses to *write a value* onto a formula column, because a formula written as a value misbehaves in Apps Script.

**A write does not require the row to have been fetched.** `update` queues its request either way and mirrors the value into local cell state only when the row is active; `validateIsWritable` needs nothing but the sheet properties. Feedback can therefore be written to every data row of a column without reading one of them.

**A queued write outlives a re-fetch in the same run.** Between a fetch and the flush, local state is the live sheet plus the queued writes: a row queued for delete stays gone however it is re-fetched or backfilled, and a cell with a queued value — its own update, else the most recently queued value fill that covers it — keeps that value once the row is fetched. Formula writes stay out of local state, so a re-fetch still shows the old effective value. The flush clears the queue, so a fetch after it integrates the live sheet only.

The corollary is the trap: **"active" means present in the working view, with row indexes still at their pre-flush positions** — not "exists on the sheet". Queued appends and removes update that view immediately; the flush is what would shift live indexes, and until then a deleted row stays inactive at the index it had when it was queued. On the `triggerOnEdit` path only the columnId row is ever fetched, so *no data row is active* — anything working from `rowIndexesActive` writes nothing at all there. `rowIndexesFull`, derived from the table bounds, is what names every data row.

**A read does require it.** `value`/`valueOrEmpty` throw when the row was never fetched, so any decision that _branches_ on a cell's current value carries a prefetch prerequisite the equivalent write doesn't. Queue the fetch in the same cycle, or decide at the call site what an unfetched row means.

**Presence in a range and presence in a payload are different facts.** A row's membership in the table buys nothing about the response: Sheets omits every cell that holds no value, no formula and no explicit number format, and a row where that is true of *every* cell comes back as a grid-data block describing each column with no `rowData` at all — or, past the populated grid, as no block at all. Measured against `Add Property Expenses` on 10 September 2026, its single blank data row sits squarely inside the table range and still arrives with no cells (#17). That is exactly the state the [blank-row](./blank-row.md) policy leaves behind, so it is ordinary rather than exceptional. `SpreadsheetRaw`'s finalize pass exists to close that gap: after integration it backfills a cell for every row and column that was fetched in full, and seeds blank **active facts** for the table columns the payload described no cell for, so a column that was fetched and is simply empty is indistinguishable from one whose top cell was empty inside a returned row. A column nobody fetched still throws, because that is a programmer error rather than an empty sheet.
