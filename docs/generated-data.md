# Generated data — do not hand-edit

Map fragment disclosed from `README.md`.

**Never read `columnConfigs.ts` whole.** `sheetConfigs.ts` is the sheet list — one labeled sheet record per line. Grep `columnConfigs.ts` for the sheet key (`"occupancy":`) and read that object only: the key opens a multi-line block, and each column config is one labeled line inside it (`columnId`, `header`, `valueName`, `isFormula`, `emptyValueAllowed`, `customDefaultValue`). Same for a single column: grep its `columnId` or name. `valueConfigs.ts` stays a pretty-printed map of member arrays.

`src/01_SpreadsheetSchema/generated/` holds the four generated data files and nothing else: `spreadsheetConfig.ts`, `sheetConfigs.ts`, `columnConfigs.ts` and `valueConfigs.ts`. Each is one literal passed through its validating constructor (`makeSpreadsheetConfig`, `makeSheetConfigs`, `makeColumnConfigs`, `makeValueConfigs`), imported from `../makeConfigs`. The hand-written half sits one level up at the Schema tier root: the generator helpers in `makeConfigs.ts`, and a sibling types file per constant (`spreadsheetConfigTypes`, `sheetConfigsTypes`, `columnConfigsTypes`, `valueConfigsTypes`) holding the derived types and accessor functions built on the data.

All four are (or are meant to be) mechanically generated from the real spreadsheet, not hand-authored:

- **`sheetConfigs`** (`01_SpreadsheetSchema/generated/sheetConfigs.ts`) — generated by `SheetConfigOperator` (`05_Operators`), reading the real "Sheet Config" sheet by name. **`hasIdColumn` is *sampled*** at emit time from whether the described sheet's header row contains the configured ID header, not from a Sheet Config checkbox. Let api access and ID prefix stay human declarations on that sheet. Non-empty ID prefixes must be unique across those entries; empty prefixes are allowed and ignored for uniqueness. The generated constructor and Sheet Config emit share that check.
- **`columnConfigs`** (`01_SpreadsheetSchema/generated/columnConfigs.ts`) — generated by `ColumnConfigOperator` (`05_Operators`) from the "Column Config" sheet. No longer stores a column's index (`colIndex`) — `03_SpreadsheetIdentified` resolves that live from `columnId` instead, since a stored index would go stale as columns are added/removed/reordered. Per column, `columnId`/`valueName`/`header`/`isFormula`/`emptyValueAllowed` are generated; `customDefaultValue` is always emitted at its default for now. **`emptyValueAllowed` is *declared*** — read straight off the column's own box in Column Config (#13), which the correction pass never rewrites, so a tick survives a sync. A column nobody has ticked emits `false`, which is what every column emitted before, so ticking is opt-in one column at a time; don't bulk-tick formula columns, since a formula that yields a blank under some conditions and a value under others is exactly the case worth declaring individually. **`isFormula` is *sampled* — read off the described column's top data-row cell at emit time (`activeIsFormula`), not declared, and not stored on Column Config** — so it can flip between regenerations if someone edits that cell. Fine as data; treat it with care as a *type* axis, since a routine `gen:configs` run can then change which columns satisfy a constraint, and the resulting error surfaces far from the spreadsheet edit that caused it. A boolean trait in the generated data does keep its literal type per column, because `boolean` is a union of literal types and contextual typing doesn't widen it — that's what lets `ColumnIsFormula` resolve to `true` or `false` rather than `boolean`, and it holds for any boolean trait the config gains later. `customDefaultValue` is meant to override what a column writes when something fills it with a default, the way `updateToDefault` and the default-append path do, but it isn't implemented and may be dropped if no use case turns up — don't repurpose it for something else in the meantime (a read-time coercion, say, belongs on the value schema rather than on a per-column trait; #12).

  **`valueName` is declared-first, sampled only as a fallback.** The sync resolves it in six steps, first match winning: the ID column is always `id`; then a `=valueConfig[...]` data-validation rule names its value; then the column's own **declared column type** — the one an operator picks in the Sheets column-type menu, delivered as `columnType` on the table's `columnProperties` — maps to a primitive (`DOUBLE`/`CURRENCY`/`PERCENT` → number, `DATE` → date, `TIME`/`DATE_TIME` → **number**, `TEXT` and the chip types → string, `BOOLEAN` → **checkbox**; `DROPDOWN` and `COLUMN_TYPE_UNSPECIFIED` map to nothing and fall through); then **BOOLEAN data validation** (Insert > Checkbox) on the Table column, or on the first data row if the Table did not name BOOLEAN, declares **checkbox** (`condition.type === BOOLEAN`, no values list required; other condition types are ignored here); then a **compatible number format** on the first data row maps to a primitive (`NUMBER`/`CURRENCY`/`PERCENT`/`SCIENTIFIC`/`TIME`/`DATE_TIME` → number, `DATE` → date, `TEXT` → string; omitted or `NUMBER_FORMAT_TYPE_UNSPECIFIED` map to nothing). Compatible means the name the sample would guess from that row equals the format's mapped name; a blank counts because that guess already consults the format. An incompatible sample stays a guess and stays untyped. **`checkbox` is produced by declaration and by nothing else** (#12, #42) — the type menu or BOOLEAN validation, never the sample: a column that merely holds `TRUE` still produces `boolean` and stays untyped. Declaring checkbox is what buys the never-blank guarantee, so a column that samples as boolean satisfies neither the selector nor the checkbox operator, and the fix is to declare it in Sheets rather than to widen the filter. Only when nothing declares it does the old top-data-row sample decide. **A compatible number format is a declaration, not a guess** (#42), including a blank first data row that inherited Currency — the type menu is never rewritten. Measured on Occupancy, 10 September 2026: "Next terms notes" was blank, undeclared and `CURRENCY`-formatted, and generated as a number; that column is now declared number and leaves the untyped list. A notes column that already contains text stays guessed string and untyped. **Only a whole-day column is a `date`** (#15) — a value name whose type is `DateSerial`, which a time-of-day serial would not satisfy, so the datetime formats map to plain numbers until there is a datetime value name to give them. Because a column left on Automatic with no mapped format and no Insert > Checkbox declares nothing, the sample is still doing real work: **the sync counts every column whose value name it had to guess and returns a one-line summary**, which the config-sync endpoint writes into its run status cell; the per-sheet breakdown goes to the execution log. The sync never fails over an untyped column — it also writes missing column IDs and appends Column Config rows, and a throw would discard all of that. **That run status cell is written by the endpoint, not by the sync.** `npm run gen:configs` calls `ConfigOrchestrator` on the Node host, so it writes no start time and no run status — to see the summary on the sheet, tick the sync endpoint's checkbox instead. On the command line the summary rides back with the four file sources (`ConfigRegeneration.untypedColumnsSummary`) and the script prints it, because a command line has no cell to write into and the only signal the sync produces would otherwise be lost; the per-sheet breakdown still goes to the log. **The agent must report that count**, per the standing permission in [`docs/how-it-runs.md`](./how-it-runs.md). **The generated entry itself never says which step decided it.** A declared `CURRENCY` column type and a `CURRENCY` number format under a blank top cell both emit `valueName: "number"`, so a wrong value name in `columnConfigs.ts` doesn't tell you whether to change a declaration or add one. That summary is the only signal the app gives; from outside it, read the live declared types directly (see [`docs/how-it-runs.md`](./how-it-runs.md) "The `gsheets` MCP tools").

  **A live config-sheet column exists so the host can identify the row (Sheet GID; Column ID on Column Config) or so a human can use it on that sheet** (readable identity such as sheet title and header; declarations such as Empty value allowed, Custom default value, Let api access, ID prefix; helper formulas). Sampled generated traits — `isFormula`, `valueName`, `hasIdColumn` — do not earn a cell. Emit still writes those traits into the generated files from the described live columns; leftover Is formula / Value title / Has ID column cells, while those columns still exist, are ignored (#33).

  **The sync doesn't only append rows — it rewrites existing ones.** Its correction pass walks *every* active Column Config row and rewrites that row's sheet title and header from the live tab and header, rows describing the config sheets themselves included — and Sheet Config's sheet title the same way. It does not rewrite sampled traits onto the config sheets. A header change still propagates on the next run with no hand edit; a value-name or formula-ness change propagates in the generated files because emit samples the live column, not because a staging cell was corrected. The config-sheet floor below holds because those particular columns don't change, not because the sync skips their rows — and when one of them genuinely does change, the floor moves with it, as it did when Sheet Config's checkbox columns picked up the `checkbox` value name (#12).
- **`valueConfigs`** (`01_SpreadsheetSchema/generated/valueConfigs.ts`) — generated by `ValueConfigOperator` (`05_Operators`) from the live "Value Config" sheet, once `columnConfigs` is already synced. After Column Config sync it still catalogs only distinct non-framework value titles in use, as Value Config headers; it asks Column Config for that title list, which walks identity rows (Sheet GID, Column ID) and reads each described column's live value title. **`makeValueConfigs` takes a `const` type parameter, and must keep it** (#18): without it the generated member lists infer as `string[]` and every dropdown column's value type collapses to bare `string`, which silently removes the union a switch over a Value Config's members is meant to be exhaustive against. The generated file carries no `as const` of its own, so the constructor is the only thing holding the literals. Measured at ~41k instantiations — see [type-check cost](./architecture/type-check-cost.md).
- **`spreadsheetConfig`** (`01_SpreadsheetSchema/generated/spreadsheetConfig.ts`) — the constraints every sheet in the spreadsheet must be written to satisfy: uniform-row indexes and the ID delimiter. The test for what belongs here is *scope, not kind* — a constant governing how any sheet must be authored belongs here even if only one tier reads it; a constant governing one tier's internal behavior does not. Config-sheet GIDs live on `sheetConfigs`, not here. Generated by `SpreadsheetConfigOperator` (`05_Operators`) from the live "Spreadsheet Config" sheet: one data row of base-1 indexes (labels say so) translated once into today's base-0 field names. The first data row is the Table header row plus one and is not stored on the layout record. The four uniform-row indexes must be integers ≥ 0, pairwise distinct, and none may equal the first data row; the generated constructor, live overlay, and Spreadsheet Config fetch share that check. Extra columns are ignored. Spreadsheet Config cells are never rewritten. A regen or checkbox sync fails closed unless that sheet has a uniquely findable Table header row and a Table with exactly one data row, with every guaranteed cell present, non-blank, and (for an index) an integer ≥ 1.

**`spreadsheetConfig`, `sheetConfigs`, `columnConfigs`, and `valueConfigs` must always be regenerated together, in the same run — never a subset of them.** Sheet names live as keys in `sheetConfigs.ts`, and `columnConfigs.ts` is keyed by those same names; `valueConfigs.ts` in turn depends on `columnConfigs` already being current to know which columns' headers to read. Regenerating a subset after a sheet/column was renamed/added/removed leaves the others referencing stale names, which breaks `npm run tsc` in places that look unrelated (the generated files themselves, plus any hand-written code — like `SheetNameGroups.ts` — that references a sheet name by string literal). Regenerate all four with `npm run gen:configs` (see [`docs/how-it-runs.md`](./how-it-runs.md), which also holds its standing-permission conditions), which runs `ConfigOrchestrator` (`05_Operators`) **on the Node host**: it reads live Spreadsheet Config (without the Table-placement check) and overlays that record on `ssConfigGet` for the rest of the run, syncs the live Sheet Config sheet, then the live Column Config sheet (including adding any missing column IDs to business sheets), flushes all of that in one write, then reads the live Value Config sheet, and only then emits source for all four files. **Live Table sampling on that run — Table header row, column-ID row, first data row — is for this run's Let api access sheets**, after Sheet Config is loaded, not for every tab. Everyday Table-placement and extra-Table checks still use last-generate sheet GIDs, one regen behind the live box. The npm script writes all four files or none, and runs `npm run tsc` itself afterward so a stale hand-written reference surfaces immediately.

**There is exactly one way to regenerate, and the `clasp run` path is gone.** The command used to ask Google to execute `generateConfigFiles` inside the Apps Script project, which holds whatever was last pushed — so editing a config operator locally left `gen:configs` silently running the previously pushed generator, and a generator failure came back as a JSON error blob rather than a stack trace. It now runs the generator in your working tree. Keeping both paths would create two regenerations that can disagree about what the config sheets say, which is the hazard the never-run-a-partial-regeneration rule exists to prevent.

**A sheet's key in `sheetConfigs`/`columnConfigs` is derived from its tab title**, so a misspelled tab becomes a misspelled identifier in the generated files and in every string literal naming that sheet. Fix a tab's spelling before code references it; afterwards it costs a sheet edit, a regeneration and every call site.

`ConfigOrchestrator.syncConfigSheetRows()` bootstraps the same live Spreadsheet Config overlay, then syncs the live Sheet Config/Column Config sheets, without writing TypeScript files. It is reachable from the sheet as a `06_API` endpoint (the run flushes after the action returns). `syncAndFlushConfigSheets()` is that same sync plus an in-orchestrator flush, used from tests. From the terminal, `npm run gen:configs` overlays live Spreadsheet Config, does that sync, then regenerates all four files, so there is no separate sync-only command.

Do not hand-edit (or AI-edit) the literal data inside `spreadsheetConfig`/`sheetConfigs`/`columnConfigs`/`valueConfigs` once they have real generators — always regenerate from the spreadsheet instead. Structural/type changes around them (not the data itself) are fine. A sheet-shape bug is fixed on the sheet, then regenerated; after any sheet change, read the regenerated entry before building on it.

**Exception — the config-sheet floor.** `sheetConfigs`/`columnConfigs` entries describing the four config-describing sheets themselves — `sheetConfig`, `columnConfig`, `spreadsheetConfig`, and `valueConfig` — are guaranteed to always be as they are, regardless of what a regeneration run produces. Config operators need _some_ fixed way to find those sheets and their own columns (including Spreadsheet Config's GID and guaranteed headers) before they can generate anything else, so these entries form a floor underneath the rest of the generated data rather than being freely regenerable. `spreadsheetConfig` the generated layout record is not part of that floor. The live floor cells now carry edit warnings, applied by the `ensureConfigSheetFloor` chore, not yet enforced by the config sync or `gen:configs`. Don't "fix" these entries by trying to regenerate them away.
